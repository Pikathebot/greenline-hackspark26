## Request lifecycle

1. The frontend loads: `GET /api/cases` (case list) and polls `GET /api/health` every 3 s.
2. The user starts a case: `POST /api/cases/{id}/runs` with `{mode: 'live'|'demo', budget:
   'normal'|'tight'}` returns `{runId}`. The server inserts a `runs` row (`status=running`) and
   spawns the graph (live) or the demo player (demo) as an `asyncio` task.
3. The frontend opens `GET /api/runs/{runId}/stream` (SSE). The server **subscribes to the bus
   first**, then sends all already-persisted events, then tails live events, deduping by `seq`.
4. Each node calls the emitter, which stamps `t`, validates against the contract, persists, and
   publishes. The SSE generator writes `id: <seq>` and `data: <json>`.
5. The run ends with exactly one `done`. The server sets `runs.status=complete` (or `error`) and
   `outcome`, then closes the bus topic, which ends the SSE response.
6. A refresh mid-run is just step 3 again. The persisted prefix is re-sent and the frontend rebuilds
   state from scratch by reducing, so no special code is needed.

## The seam

The **only** coupling between frontend and backend is:

1. `04-EVENT-CONTRACT.md`: `GreenlineEvent` v2 and `FailureCase`, typed in TS
   (`frontend/src/contract/`) and Pydantic (`backend/greenline/events/models.py`).
2. The REST + SSE endpoints in `05-BACKEND-SPEC.md` § API.

If the frontend needs data no event carries, **add a field or variant to the contract** in both
languages, in one commit, and tell your partner. Never side-channel it.

## Config (`backend/.env`, prefix `GREENLINE_`)

| Var | Default | Meaning |
|---|---|---|
| `GREENLINE_MODEL_URL` | `http://127.0.0.1:8080` | Generation server |
| `GREENLINE_EMBED_URL` | `http://127.0.0.1:8081` | Embedding server |
| `GREENLINE_MODEL` | `qwen3-8b` | Model tag shown in UI and `run.start.model` |
| `GREENLINE_MODELS_DIR` | `models` | GGUF folder relative to `backend/`, read by `scripts/llama-*.ps1`. Pre-staged, gitignored. |
| `GREENLINE_SANDBOX_IMAGE` | `greenline-sandbox:latest` | Built from `greenline/sandbox/Dockerfile` |
| `GREENLINE_DB_PATH` | `greenline.db` | Relative to `backend/` |
| `GREENLINE_FIXTURE_REPO` | `fixtures/ledger-core` | Relative to `backend/` |
| `GREENLINE_MAX_MODEL_CALLS` | `16` | Normal budget, per run |
| `GREENLINE_MAX_TOOL_CALLS` | `16` | Normal budget (sandbox runs), per run |
| `GREENLINE_MAX_ELAPSED_MS` | `180000` | Normal budget, per run |
| `GREENLINE_TIGHT_MODEL_CALLS` / `_TOOL_CALLS` / `_ELAPSED_MS` | `4` / `3` / `60000` | The Tight preset |
| `GREENLINE_RERUN_CONCURRENCY` | `1` | Containers at once during Reproducer (try 2–3 at B7) |
| `GREENLINE_DRY_RUN` | `true` | Simulated PRs |
| `GITHUB_TOKEN` | (empty) | Only when `DRY_RUN=false` |
| `GREENLINE_CORS_ORIGINS` | `http://localhost:5173` | Only needed if not using the Vite proxy |

The frontend has one env var: `VITE_API_TARGET` (proxy target, used only by `vite.config.ts`).
