> **Use HTTPS, not SSH.** `gh` is set to SSH on B's laptop but `ssh -T git@github.com` fails with

## 4. The working rhythm

- **Branch policy: everyone commits straight to `main`.** Two people, separate folders
  (`backend/` is B's, `frontend/` is A's), so conflicts are rare and branches cost more time than
  they save. The only shared files are `docs/` and the two contract files.
- **Commit after every ticket**, message starts with the ticket id:
  `B5: sandbox runner — 0142 x10 shows mixed results` or `A4: AgentGraph — barrier on protected_file`.
- **Push after every ticket and at every phase boundary** (table below). A ticket that is not
  pushed does not exist: if a laptop dies, or you have to move venue, only pushed work survives.
- **Before every push:** `git pull --rebase`, then `git push`. If the rebase conflicts, fix it,
  `git add <file>`, `git rebase --continue`. Never `git push --force` on `main`.
- Check `git status` before `git add -A`. If anything under `models/`, `.venv`, or `.env` shows up,
  stop.
- `git log --oneline -10` and `git diff` are your undo and your memory. Commit **before** letting
  Claude Code attempt anything large; `git restore .` undoes it.

```powershell

```

A tag is an instant rollback point: `git checkout cp1` shows exactly what you demoed at CP1.

## 5. The 15:45 pre-move ritual (both people)

1. `git status` clean? Commit what's there as `WIP: ...` if it must be (WIP on `main` is fine here).
2. `git pull --rebase`, `git push origin main`, `git tag pre-move && git push origin pre-move`.
3. Confirm on github.com that the latest commit shows.
4. Stop uvicorn, Vite, both `llama-server`s. `docker ps -a` empty. Then close lids / pack.
5. At the new venue: `git pull --rebase` (to pick up the partner's last push), then the env
   check. **Your IP changes**: update `frontend/.env.local` (`VITE_API_TARGET=http://<B-ip>:8000`),
   which is gitignored, so it will not collide.

## 6. Keep the demo alive while you keep building (worktree)

Judges may be at your booth for hours at CP2 while you want to keep building. Never demo from the


Notes: the worktree has no `node_modules`, `.venv` or models (all gitignored). Either install again in

`backend/.env`, which is gitignored). B's laptop is the demo backend, so B does this one.

## 7. If something goes wrong

| Problem | Fix |
|---|---|
| `git push` rejected (non-fast-forward) | `git pull --rebase`, resolve, `git push`. Never force. |
| Push dies on a huge file | You committed a model or db. `git reset --soft HEAD~1`, add it to `.gitignore`, `git rm --cached <path>`, recommit. If it's already pushed, tell your partner, do not force-push alone. |
| Conflict in `docs/` or a contract file | The one file both edit. Whoever pushed first wins the structure; the other re-applies their change on top. Contract changes are additive only, in both languages, one commit, announced aloud. |
| `Permission denied` / 403 on push | The invite is not accepted yet (§1), or `gh auth status` shows the wrong account. |
| Laptop dies | Clone on the spare: `git clone https://github.com/Pikathebot/greenline-hackspark26.git D:\greenline` into an empty folder, then copy `backend\models\` from the USB drive. |
| Venue Wi-Fi blocks GitHub | Phone hotspot. Last resort: `git bundle create x.bundle --all` onto the USB drive and `git pull x.bundle main` on the other laptop. |
| Committed `.env` with a secret | Rotate the secret. Don't try to hide it with a later commit. |
